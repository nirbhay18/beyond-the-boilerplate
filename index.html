Step 1 · Write the rules down once

A rules file your AI reads on every request

Most AI coding tools load a project instructions file automatically. The name depends on the tool, the idea doesn’t: name the exact functions you expect, the commands to run, and what “done” means.

ToolFile
Most agents (Codex, Copilot, Cursor, and others)AGENTS.md

GitHub Copilot.github/copilot-instructions.md
Generate one for your plugin → Download the full template

Rule of thumb: if a line wouldn’t change what the model writes, delete it. Short files get followed.

AGENTS.md (excerpt)
## Security (non-negotiable)
- Input: wp_unslash() first, then sanitize:
  sanitize_text_field(), absint(), sanitize_email()
- Output: escape late, for the context:
  esc_html(), esc_attr(), esc_url(), wp_kses_post()
- Every state change: nonce AND capability.
  check_admin_referer() + current_user_can()
- SQL only via $wpdb->prepare() or insert().
- REST routes get a real permission_callback.

## Workflow
- Propose the file tree first. Wait.
- One class per file, PSR-4, in src/.
- Run composer lint before saying "done".

## Never
- Write "// TODO: add security later". We both know.
- Silence errors with @ or error_reporting( 0 ).

Step 3 · Make the checks non-optional

The starter kit

Drop these into your plugin’s root. Replace my-plugin, myplugin and MyVendor\MyPlugin with your own. Then composer install and composer lint.

phpcs.xml.dist

WordPress Coding Standards with your text domain, prefixes and minimum versions.
phpcs.xml.distDownload
<?xml version="1.0"?>
<ruleset name="My Plugin">
	<file>.</file>
	<exclude-pattern>/vendor/*</exclude-pattern>
	<exclude-pattern>/node_modules/*</exclude-pattern>
	<exclude-pattern>/build/*</exclude-pattern>
	<exclude-pattern>/tests/*</exclude-pattern>
	<arg name="extensions" value="php"/>
	<arg value="sp"/>

	<!-- Minimum versions you support. -->
	<config name="minimum_wp_version" value="6.5"/>
	<config name="testVersion" value="7.4-"/>

	<!-- Core + Docs + Extra, security sniffs included. -->
	<rule ref="WordPress"/>
	<rule ref="PHPCompatibilityWP"/>

	<rule ref="WordPress.WP.I18n">
		<properties>
			<property name="text_domain" type="array">
				<element value="my-plugin"/>
			</property>
		</properties>
	</rule>

	<rule ref="WordPress.NamingConventions.PrefixAllGlobals">
		<properties>
			<property name="prefixes" type="array">
				<element value="myplugin"/>
				<element value="MyVendor\MyPlugin"/>
			</property>
		</properties>
	</rule>

	<!-- PSR-4 class files in src/. -->
	<rule ref="WordPress.Files.FileName">
		<exclude-pattern>/src/*</exclude-pattern>
	</rule>
</ruleset>

.github/workflows/ci.yml

Lint, analyse and run the official Plugin Check action on every push and pull request.
.github/workflows/ci.ymlDownload
name: CI
on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.2'
          tools: composer
          coverage: none
      - run: composer install --no-interaction --no-progress
      - name: Coding standards (PHPCS + WPCS)
        run: composer lint
      - name: Static analysis (PHPStan)
        run: composer analyse

  plugin-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Plugin Check
        uses: wordpress/plugin-check-action@v1

The feedback loop

The trick that saves the most time: the linter report is the next prompt.
terminal
# 1. Let phpcbf fix the formatting noise
composer lint:fix

# 2. Hand what's left back to your AI tool, e.g.:
> Run composer lint. Fix every reported error.
> Don't rewrite unrelated code. Run it again until it's clean.

# 3. Plugin Check, before anything ships
wp plugin check my-plugin

Tested with WordPress Coding Standards: the talk’s draft-1 testimonials handler fails with 16 errors; the fixed draft 2 passes with 0 errors and one expected warning for its custom-table insert.

Step 4 · Anyone can say “looks good.” Shipping needs a review.

Four questions before every merge

Don’t read AI code top to bottom. Trace these four things. They map closely to what a security audit asks.

Input

Is every $_GET and $_POST unslashed and sanitized? Is it validated against what you actually allow, not just cleaned?

Output

Is it escaped at the moment it’s printed, with the function for that context: esc_html(), esc_attr(), esc_url()?

Access

A nonce on every state change? current_user_can() before acting? A permission_callback that isn’t just __return_true?

Data

$wpdb->prepare() on every query? Does uninstall.php clean up options, tables and cron events?
